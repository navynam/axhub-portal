# AX-HUB 백엔드 개발 가이드

> 대상: 백엔드를 처음 이어받는 **초급 개발자**.
> 목적: 실행 방법 → 패키지/레이어 규칙 → 공통 컴포넌트 사용법 → 새 도메인을 표준 패턴으로 채우는 절차를 순서대로 익힌다.
> 정답지: `agent` · `permission` 두 도메인이 완성 예시다. 나머지(`knowledge`/`community`/`resource`/`auth`)는 이 둘을 보고 동일하게 채운다.

---

## 1. 실행 방법

### 1.1 요구 사항 / 스택
| 항목 | 값 | 근거 |
|------|-----|------|
| Java | 17 | `build.gradle` `sourceCompatibility = '17'` |
| Framework | Spring Boot 3.2.5 (Web / Data JPA / Security / Validation) | `build.gradle` |
| 인증 | JWT `io.jsonwebtoken:jjwt 0.11.5` | `build.gradle` |
| DB | H2 인메모리(개발) → PostgreSQL/MySQL(운영) | `build.gradle`, `application.yml` |
| 기타 | Lombok, Gradle | `build.gradle` |

### 1.2 실행
```bash
cd backend
./gradlew bootRun        # http://localhost:8080
```
- H2 콘솔: `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:mem:axhub`, user `sa`, 비밀번호 없음).
- 프론트 실연동: `axhub-portal/.env` 에 `VITE_USE_API=true`, `VITE_API_BASE=http://localhost:8080/api/v1`.

### 1.3 application.yml 요지
| 설정 | 값 | 의미 |
|------|-----|------|
| `server.port` | 8080 | 서버 포트 (context-path `/`, 경로 접두어 `/api/v1` 는 컨트롤러에서 부여) |
| `spring.datasource.url` | `jdbc:h2:mem:axhub;...;MODE=PostgreSQL` | 인메모리 H2, PostgreSQL 호환 모드 |
| `spring.jpa.hibernate.ddl-auto` | `create-drop` | 재시작 시 스키마 재생성(개발용). **운영은 `validate`/`none`** |
| `spring.jpa.show-sql` | true | 실행 SQL 콘솔 출력 |
| `axhub.jwt.secret` / `expire-minutes` | 더미 시크릿 / 120 | JWT 서명 키·만료. **운영은 환경변수/시크릿 주입** |
| `axhub.cors.allowed-origins` | `http://localhost:5173` | 프론트 개발 서버 허용 출처 |

## 2. 패키지 구조 지도

```
backend/src/main/java/com/axhub/
├─ AxhubApplication.java      진입점 (@SpringBootApplication + @EnableJpaAuditing)
├─ common/                    ★ 공통 (모든 도메인이 사용)
│  ├─ response/ApiResponse        {success,data,message} 표준 응답 래퍼
│  ├─ exception/BusinessException      업무 예외 (status + message)
│  ├─ exception/GlobalExceptionHandler 전역 예외 → 표준 실패 응답 변환
│  ├─ config/SecurityConfig      보안(JWT·CORS). 현재 permitAll
│  └─ entity/BaseTimeEntity      createdAt/updatedAt 자동 기록 (MappedSuperclass)
├─ agent/         ✅ 레퍼런스 구현
│  ├─ AgentController.java   REST 엔드포인트
│  ├─ AgentService.java      업무 로직 + 트랜잭션
│  ├─ AgentRepository.java   Spring Data JPA
│  ├─ domain/Agent.java      엔티티 (DB 매핑 + 도메인 로직)
│  └─ dto/AgentResponse.java 응답 DTO(record)
├─ permission/    ✅ 레퍼런스 구현 (요청·승인 흐름)
│  ├─ PermissionController / PermissionService / PermissionRequestRepository
│  ├─ domain/PermissionRequest.java
│  └─ dto/CreateRequestDto.java, RequestResponse.java
├─ knowledge/     🔧 스캐폴드 (KnowledgeController 만)
├─ community/     🔧 스캐폴드 (CommunityController 만)
├─ resource/      🔧 스캐폴드 (ResourceController 만)
└─ auth/          🔧 스캐폴드 (AuthController 만)
```

### 도메인 표준 5요소 (매 도메인 동일)
```
com.axhub.<도메인>
├─ <도메인>Controller.java   REST 엔드포인트 (얇게 유지, DTO in/out)
├─ <도메인>Service.java      업무 로직 + @Transactional
├─ <도메인>Repository.java   Spring Data JPA 인터페이스
├─ domain/<엔티티>.java       DB 매핑 + 도메인 로직 메서드
└─ dto/*.java                요청/응답 DTO (record)
```

## 3. 레이어 규칙 (반드시 지킬 것)

```
요청 → Controller → Service → Repository → DB
       (얇게)     (로직/트랜잭션)  (JPA)
응답 ← DTO 변환 ←──┘
```

| 레이어 | 책임 | 하지 말 것 |
|--------|------|-----------|
| **Controller** | HTTP 매핑, 요청 바디 수신, `ApiResponse.ok(...)` 로 감싸 반환 | 업무 로직·DB 접근 금지 (얇게 유지) |
| **Service** | 업무 로직, 트랜잭션(`@Transactional`), 엔티티↔DTO 변환, 예외(`BusinessException`) 발생 | 컨트롤러/HTTP 세부 의존 금지 |
| **Repository** | DB 접근 (`JpaRepository` + 메서드명 쿼리) | 로직 넣지 않기 |
| **domain(Entity)** | 테이블 매핑 + 도메인 로직(예: `toggleActive()`) | setter 남발·외부 `new` 금지 (`@NoArgsConstructor(PROTECTED)`) |
| **dto** | 요청/응답 전용 `record`. 엔티티 대신 노출 | — |

핵심 원칙 (agent 도메인이 보여주는 것):
- **엔티티 직접 노출 금지** → 항상 DTO(record)로 변환(`AgentResponse.from(entity)`). 순환참조·불필요 필드 노출·스펙 결합 방지.
- **조회는 `@Transactional(readOnly = true)`**, 변경은 `@Transactional`.
- **도메인 로직은 엔티티 안에** 두기(`Agent.toggleActive()`, `PermissionRequest.approve()`).
- **생성자 주입**: `@RequiredArgsConstructor` + `final` 필드(Lombok).

## 4. 공통 컴포넌트 사용법

### 4.1 ApiResponse (표준 응답)
```java
// 성공
return ApiResponse.ok(agentService.getAgents());   // {success:true, data:[...], message:null}
// 본문 없는 성공(삭제 등)
return ApiResponse.ok(null);
```
`ApiResponse.fail(message)` 는 `GlobalExceptionHandler` 내부에서만 사용한다(컨트롤러에서 직접 실패 응답을 만들지 않는다).

### 4.2 BusinessException (업무 예외)
서비스에서 "예상된" 오류를 던지면 `GlobalExceptionHandler` 가 표준 실패 응답으로 바꾼다.
```java
// 단축 생성자
throw BusinessException.notFound("Agent 를 찾을 수 없습니다: " + id);   // 404
throw BusinessException.badRequest("반려 사유는 필수입니다.");           // 400
// status 직접 지정
throw new BusinessException(HttpStatus.FORBIDDEN, "도구 권한이 없어 실행할 수 없습니다."); // 403
```
`@Valid` 검증 실패는 자동으로 400 + `"필드명: 메시지"` 로 변환된다(직접 처리 불필요).

### 4.3 BaseTimeEntity (생성/수정 시각)
엔티티가 `extends BaseTimeEntity` 하면 `createdAt`/`updatedAt` 이 JPA Auditing 으로 자동 기록된다.
- 전제: `AxhubApplication` 의 `@EnableJpaAuditing` (이미 설정됨).
- DTO 로 노출할지는 선택(현재 agent/permission DTO 는 시각 필드 미노출).

### 4.4 SecurityConfig (JWT/CORS) 개요
- 현재 `anyRequest().permitAll()` — **모든 요청 무인증 통과**(개발 편의). CSRF off, 세션 STATELESS.
- CORS: `http://localhost:5173` 출처, `GET/POST/PUT/PATCH/DELETE/OPTIONS`, 모든 헤더, credentials 허용.
- 인증 강화 순서(주석의 TODO): ① `JwtProvider`(발급/검증) → ② `JwtAuthFilter` `addFilterBefore` 등록 → ③ `requestMatchers("/api/v1/auth/**").permitAll().anyRequest().authenticated()`.

## 5. 새 도메인 추가 실습 — agent 를 정답지로 knowledge 채우기

`knowledge` 는 현재 `KnowledgeController` 골격만 있고 빈 배열을 반환한다.
`agent` 패턴을 그대로 복제해 **Entity → Repository → DTO → Service → Controller** 순으로 채운다.
(엔티티부터 만들면 다음 레이어가 참조할 타입이 준비되어 편하다.)

### 목표 계약 (프론트 `knowledgeService.js` 기준)
| 메서드 | 경로 | 프론트 함수 |
|--------|------|-------------|
| GET | `/knowledge?category=&scope=&q=` | `fetchKnowledge(params)` |
| GET | `/knowledge/categories` | `fetchCategoryTree()` |
| GET | `/knowledge/{id}` | `fetchKnowledgeDetail(id)` |

### STEP 1. domain — `knowledge/domain/Knowledge.java`
`Agent.java` 를 참고. 프론트 `models/types.js` 의 `Knowledge` 필드와 맞춘다.
```java
@Entity
@Table(name = "knowledge")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Knowledge extends BaseTimeEntity {
    @Id @Column(length = 20)
    private String id;              // 예: 'kb-01'
    private String name;
    private String description;
    private String owner;
    private String scope;           // enum 으로 승격 가능
    private String perm;
    private int docs;               // 문서 수
    private int linked;             // 연결 Agent 수
    private String category;        // 카테고리 트리 leaf id
    // 필요 시 도메인 로직 메서드 추가
}
```

### STEP 2. Repository — `knowledge/KnowledgeRepository.java`
`AgentRepository` 와 동일하게 인터페이스만. 필터는 메서드명 쿼리로.
```java
public interface KnowledgeRepository extends JpaRepository<Knowledge, String> {
    List<Knowledge> findByCategory(String category);
    List<Knowledge> findByScope(String scope);
}
```

### STEP 3. dto — `knowledge/dto/KnowledgeResponse.java`
`AgentResponse` 처럼 `record` + `from(entity)` 정적 변환.
```java
public record KnowledgeResponse(
        String id, String name, String desc, String owner,
        String scope, String perm, int docs, int linked, String category) {
    public static KnowledgeResponse from(Knowledge k) {
        return new KnowledgeResponse(k.getId(), k.getName(), k.getDescription(),
                k.getOwner(), k.getScope(), k.getPerm(), k.getDocs(), k.getLinked(), k.getCategory());
    }
}
```

### STEP 4. Service — `knowledge/KnowledgeService.java`
`AgentService` 패턴: 조회 `readOnly`, 없으면 `BusinessException.notFound`.
```java
@Service
@RequiredArgsConstructor
public class KnowledgeService {
    private final KnowledgeRepository repository;

    @Transactional(readOnly = true)
    public List<KnowledgeResponse> getKnowledge(String category, String scope, String q) {
        // 필터 분기(간단히 findAll 후 조건 필터 또는 메서드명 쿼리 사용)
        return repository.findAll().stream().map(KnowledgeResponse::from).toList();
    }

    @Transactional(readOnly = true)
    public KnowledgeResponse getOne(String id) {
        Knowledge k = repository.findById(id)
                .orElseThrow(() -> BusinessException.notFound("지식을 찾을 수 없습니다: " + id));
        return KnowledgeResponse.from(k);
    }
}
```

### STEP 5. Controller — `knowledge/KnowledgeController.java` (기존 골격 대체)
스캐폴드의 빈 반환을 서비스 호출로 교체. `@RequestMapping` 경로는 유지.
```java
@RestController
@RequestMapping("/api/v1/knowledge")
@RequiredArgsConstructor
public class KnowledgeController {
    private final KnowledgeService service;

    @GetMapping
    public ApiResponse<List<KnowledgeResponse>> list(
            @RequestParam(required = false) String category,
            @RequestParam(required = false) String scope,
            @RequestParam(required = false) String q) {
        return ApiResponse.ok(service.getKnowledge(category, scope, q));
    }

    @GetMapping("/{id}")
    public ApiResponse<KnowledgeResponse> detail(@PathVariable String id) {
        return ApiResponse.ok(service.getOne(id));
    }
    // /categories 는 KnowledgeCategory(부모/자식) 엔티티 추가 후 별도 구현
}
```

> `community`(Board), `resource`(도구 권한 맵), `auth`(JwtProvider/UserRepository)도 같은 5단계를 반복한다.
> `resource` 요청 생성은 새 로직을 만들지 말고 `PermissionService.create(...)` 를 재사용하는 것이 설계 의도다.

## 6. 프론트 연동 체크리스트

새/변경 API 를 프론트와 붙일 때 확인할 것.

1. **경로 일치**: 백엔드 `@RequestMapping`+`@*Mapping` 경로가 프론트 service 의 `http.get/post/...('...')` 와 정확히 같은가.
   (예: agent active 는 body 키 `active`, favorite 는 `fav` — 프론트 payload 키와 백엔드 파싱 키가 일치해야 함.)
2. **응답 래핑**: 컨트롤러가 `ApiResponse.ok(...)` 로 감쌌는가. (프론트 `http.js` 가 `data` 만 언랩)
3. **DTO 필드명**: 프론트 `models/types.js` / mock(`data.js`) 필드명과 DTO record 필드명이 같은가.
4. **에러**: 실패는 `BusinessException`(적절한 status)로 던졌는가. 프론트는 `HttpError.status/message` 로 처리.
5. **스위치 전환**: 프론트 `.env` `VITE_USE_API=true`, `VITE_API_BASE` 설정 후 서비스가 mock 대신 `http` 를 타는지 확인.
6. **CORS/포트**: 프론트 5173 → 백엔드 8080 요청이 `SecurityConfig` CORS 로 허용되는지.
7. **PR 규칙**: 새 API 는 프론트 service ↔ 백엔드 controller **양쪽을 같은 PR** 로 반영(ARCHITECTURE.md §5).
